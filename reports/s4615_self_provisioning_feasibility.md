# S4615 — faisabilité d'auto-provisioning (A4H/600/ABDELJ, READ ONLY)

**Verdict court :** le socle commercial `1010/10/00` et les extensions client ont des précédents exécutés, mais **aucune usine EUR de société `1010` ni son chemin de création/valorisation n'est prouvé**. L'auto-provisioning complet de P615-101 et du flux PGI est donc **NO-GO**. Aucun droit d'écriture nouveau n'a été testé.

GET live ciblés : `API_PLANT_SRV/A_Plant` retourne **0** usine pour `CompanyCode=1010`, mais `Plant=1710 → CompanyCode=1710` ; `API_PRODUCT_SRV/A_ProductSalesDelivery` retourne un seul produit de `1010/10`, approvisionné par `1710` ; `A_ProductValuation` retourne **0** ligne pour l'aire `1010`. `API_COMPANYCODE_SRV` avait confirmé `1010=BE/EUR` contre `1710=US/USD`. Ces API ne montrent **ni toutes les affectations d'usines**, ni les lignes brutes `T001W/T001K/TVKWZ`, ni le lien au point d'expédition `1010`.

**Permissions ABDELJ :** GET des services ci-dessus = autorisé ; des écritures ciblées antérieures (Customizing 1010, extensions du BP existant) sont attestées. Aucun refus de permission exact n'a été observé pour ces changements ; `NEEDS_PERMISSION` ne serait donc pas une conclusion étayée. Le bridge GUI courant n'autorise pas un `SE16N`/une lecture générique de `T001W/T001K/TVKWZ` via son protocole ; un contrôle GUI ciblé reste à établir, sans élargir la safety globale.
